Enterprise tenancy and data isolation

Can the two products be sold to two separate customer bases, and can a public body or a large enterprise be given its own database? Written against the code on 16 August 2026.

The answerShort version

The two products are already separated cleanly enough to sell to two different customer bases. The isolation seam that would allow a single customer to be moved onto its own database exists on the buyer side only, it has never been switched on, and nothing in the codebase can switch it on today. More useful than any of that: a dedicated database is not the thing that will block these sales, and building one first would spend the most money on the least binding constraint.

The four things that will actually stop a public sector or enterprise sale

None of them is solved by giving a customer its own database.

  1. Data is in Ireland, not the UK. Every row sits in AWS eu-west-1. The published residency page states in bold that no customer data is stored in a UK region and that region pinning is not offered on any plan.
  2. Bid content leaves the UK and the EEA for AI processing. The same page discloses Anthropic in the United States and the Gemini API as "not region-pinned by the API used". A tenant database in London would not change this.
  3. Cyber Essentials is the mandated gate, and we have not verified that we hold it. PPN 014 requires it before contract award for central government and NHS bodies. It costs £320 plus VAT at our headcount.
  4. The supplier product has no database-level tenant separation at all. It runs entirely on a key that bypasses row-level security, so isolation rests on hand-written filters in application code. This is the finding with the widest blast radius.

What to do instead of a silo

Sell three tiers, not N databases. Pooled with contractual assurances covers the whole SME and mid-market supplier base today. A single second database pinned to London (eu-west-2) serves every UK residency requirement, public sector and enterprise alike, with one extra database rather than one per customer. A true per-customer silo is priced as a bespoke engagement and sold only against a signed contract that pays for it. The detail, with costs and lead times, is in section 7.

What a customer of one product can see of the other

Separation is by entitlement and routing inside one codebase, one database and one deployment. Every route is gated by requireProductAccess(product), which resolves the caller, resolves the organisation from server-trusted membership, reads the entitlement from the product_context JSONB on the organisation, and applies a registry kill switch that fails closed on an unknown key. Product visibility is driven by product_context; the CrowMark tier within that product is resolved from product_subscriptions, with product_context.crowmark.tier as a read cache.

The commercial reading

Selling the two products to two unrelated customer bases needs no engineering. A buyer never sees supplier data and a supplier never sees buyer data. What is shared is the database, the codebase and the release train, which is what a customer's security reviewer will ask about.

Section 3How far the dedicated branch gets

The seam is real and it was designed for this question. resolveTenantDatasource(orgId, sessionClient) is described in its own header as the one seam through which every buyer database access flows. It reads a control-plane table, public.tenant_datasource_catalog, carrying organisation_id, isolation_tier, datasource_ref, connection_secret_ref and region. It runs under the caller's RLS session client and never a service-role bypass, the catalog's own policy exposes only the caller's organisation row, and the catalog schema refuses to hold a raw connection string: a future dedicated tenant may hold only a secrets-manager key. A control-plane read failure falls back to pooled rather than failing the request. This is careful work.

web/src/shared/lib/tenant/datasource.ts:1-123 · supabase/migrations/20260719000010_council06_ws6_datasource_catalog.sql:1-53

It is not a control that reaches nothing

Twelve non-test files consume the seam, plus the module itself. That is more than double the five I was briefed to expect, so the seam is better wired than the handover claimed. A static guard test globs the buyer API route tree and fails CI if a route touches the database without importing the resolver, or mints its own client.

But the promotion path does not exist, and the seam is not total

Nothing in the codebase can set a tenant to dedicated. The string "dedicated" appears exactly twice in all shipping code across web, portal and api: once in the type union, once in the guard that throws. The only writer of isolation_tier anywhere is the owner-gated provisioning route, and it hard-codes 'pooled' with datasource_ref: 'supabase:primary'. Promotion today would require a manual SQL write, after which every affected request would throw. The comment saying a tenant can "later be promoted via a catalog and config change" describes an intention, not a switch that exists.

web/src/shared/lib/tenant/datasource.ts:24,108 · apps/portal/src/app/api/customers/[id]/provision-council/route.ts:133,147-148

Half the buyer routes do not go through the seam, by design. Of 20 route files under the buyer API tree, 10 import the resolver; 9 are thin proxies forwarding to the FastAPI backend, which has no seam and no RLS (section 4); and 1 reads the database without it.

A gap in the guard, found in this review. app/api/council/buyer-profile/route.ts performs a real database read by calling loadBuyerProfile(guard.supabase, orgId), passing the raw session client rather than the resolved ds.client. The guard does not catch it: it detects database access by matching a quoted council_ table name or the token unmigratedClient in the route file, and this route scores zero on that regex because the query lives in a helper module the guard does not glob. The same helper is called with guard.supabase from two further routes that do import the seam. Security impact today is nil: the read is org-scoped and under RLS. The impact is on the claim. If a tenant were ever promoted, these reads would keep hitting the pooled primary in silence.

What a shippable silo would still need

  • A datasource runtime: a client factory per datasource_ref, connection pooling per tenant, and secret resolution from a manager we do not currently run.
  • A provisioning path that creates the project, replays all 653 migrations, seeds reference data, writes the catalog row, and can roll back a half-provisioned tenant.
  • Migration fan-out: every future migration applied to staging, to the pooled primary, and to each silo, with per-tenant schema-version tracking.
  • The same seam on the FastAPI tier, which has none at all.
  • Per-tenant backups, restore drills, alerting, log routing and cost attribution.
  • Cross-tenant reporting, which stops being one query.

Reasoning rather than citation: that list is derived from the code as it stands, not from a vendor document. The vendor evidence for why each item is expensive is in section 5.

Section 4The supplier side does not share the seam

Zero of the 57 supplier-product API routes import the resolver. The supplier side has no isolation seam, and it also has no row-level security backstop.

The reason is architectural rather than an oversight. The supplier product's Next.js routes are thin proxies that forward to the FastAPI backend on Railway. That backend reaches Postgres through PostgREST using the service role key, which bypasses row-level security entirely. I measured it: 411 get_supabase() call sites across 130 files in 315 Python modules, and supabase_anon_key referenced exactly once, by its own declaration. There is no RLS-respecting path in that tier.

Measured 2026-08-16 · api/app/services/supabase_client.py:55-67 · api/app/config.py:43. A same-day audit reports 414 by a slightly different count.

Why this matters commercially, not just technically

There is a real RLS parity gate in CI that replays every policy statement in the migrations and diffs the result against the production snapshot. It is a good control and it is worth showing a buyer. It also verifies policies that the supplier product's request path never evaluates. If we tell a supplier's security reviewer "row-level security isolates tenants", that sentence is true of the buyer product's direct reads and false of the supplier product. The reviewer will ask, and NCSC Cloud Security Principle 3 requires us to be able to explain exactly how separation is implemented.

Section 5How the market actually serves this requirement

Silo, pool and bridge

AWS names three models. Silo gives each tenant dedicated resources, for example a separate database. Pool shares resources, which AWS calls "the more classic notion of multi-tenancy". Bridge acknowledges that most real systems are mixed, some components siloed and some pooled. AWS adds a qualifier that matters for us: even a silo still runs a shared identity, onboarding and operational experience, and that is what separates SaaS from a managed service where each customer runs their own version.

What a UK public body actually asks

There is no single national security questionnaire. For cloud procurement, the G-Cloud service question set is the questionnaire, it is answered once, and it is published for anyone including competitors to read. The current framework is G-Cloud 14 (RM1557.14), live to 28 October 2026; G-Cloud 15 is in procurement with award scheduled for 6 August 2026.

The fields that bear on this analysis, verbatim from a live listing:

  • "Describe how different organisations sharing the same infrastructure are kept apart", 100 words. This is the multi-tenancy question, and it is the one this document exists to let us answer truthfully.
  • Data storage and processing locations: United Kingdom / European Economic Area / other. Plus "User control over data storage and processing locations", yes or no.
  • Protecting data at rest, Datacentre security standards, Data sanitisation.
  • Penetration testing frequency and approach. A live listing openly answers "At least once a year" and "In-house", which a buyer can see and score.
  • Standards and certifications: ISO/IEC 27001, CSA STAR, PCI, Cyber Essentials, Cyber Essentials Plus, each a yes or no.
  • End-of-contract data extraction and end-of-contract process, 200 words each.

The residency mandate people assume does not exist

Government policy is explicit: "There is no government policy which directly prevents departments or services from storing or processing cloud-based data in any specific country", and it is "the responsibility of each government department to take risk-based decisions". Cloud First tells teams to use overseas providers where due diligence supports it.

Individual departments impose UK-only by contract instead. DWP's contractor policy states that authority assets "must not be accessed, processed, transmitted and/or stored outside of the United Kingdom without the prior written consent of the Authority", and its definition of offshoring catches non-UK staff accessing data and diagnostic data sent abroad, not only where the database sits. A residency clause we sign would therefore bind our support rota, our logs, our backups and our sub-processors, which is where our AI sub-processors become the binding problem rather than the database.

What large private enterprises ask for instead

  • SOC 2 Type II report, and often a recent third-party penetration test. CREST accreditation is the usual name; NCSC's CHECK scheme is the public sector equivalent. Note NCSC's own caveat: a pen test "can only validate that your organisation's IT systems are not vulnerable to known issues on the day of the test".
  • SSO via SAML, and SCIM for provisioning. SAML gets authentication; SCIM is what closes the leaver-deprovisioning gap, which is what reviewers test.
  • Customer-managed keys (BYOK, CMEK). Worth being precise about what this buys: it is server-side encryption at rest under a key the customer can rotate, disable or destroy, which gives crypto-shredding and auditable key use. It does not protect against exposure through the application, which legitimately holds decrypt rights while serving a request. That last point is my inference from the scope of the vendor documentation, not a quoted vendor statement.
  • Contractual controls: a DPA meeting UK GDPR Article 28(3), a sub-processor list with a notice-and-object right under Article 28(2), and a breach notification clause. The ICO deadline to the regulator is 72 hours; as a processor our contractual clock to the customer is normally shorter, commonly 24 to 48 hours, to leave the controller time to file.
  • Residency as a contract term. The market-standard formulation is a commitment with carve-outs, as in AWS's "We will not move or replicate your content outside of your chosen AWS Region(s) without your agreement".

Section 6The supplier confidentiality question

The owner's framing is right and it is the sharpest question on this page. A supplier's bid, tender and contract content is commercially sensitive, and that supplier's competitors may be other tenants on the same platform. "Trust our filters" is not an answer a procurement lead will accept.

What is true today

  • No supplier tenant can read another's data through any shipped route. Every supplier route resolves the organisation from server-trusted membership, never from the request body, and a body-supplied organisation that mismatches the verified one is rejected. (api/app/dependencies/service_auth.py:85-141)
  • Buyer and supplier data are in different tables and neither product's code reads the other's, verified in both tiers.
  • There is one deliberate cross-tenant read, and it should be disclosed rather than discovered. The PPN 002 benchmark endpoint selects across all organisations' completed contracts to produce sector aggregates. It reads id, contract_value, sector, social_value_score from crowmark_contracts and full rows from crowmark_measures for a sample, aggregates them, and returns only aggregates. It is feature-gated on crowmark.benchmarks, capped, and the code comments are candid that RLS could not have bounded it. No bid narrative text is read. (api/app/routers/crowmark/analytics.py:135,181)

The exposure to fix before selling on confidentiality

A supplier asking "can my competitors see my data?" deserves the whole answer. Today the whole answer includes: your completed contract values and social-value scores contribute to a benchmark other tenants can see in aggregate, and your bid content is sent to AI sub-processors in the United States and to an endpoint that is not region-pinned. Both are defensible. Neither is currently something the customer is asked to consent to at the point it matters.

Why tier 2 beats tier 3, and it is not close

A London project pooled across all UK-residency customers answers the same procurement question as a per-customer silo, on the same G-Cloud form, for one extra database instead of N. It converts every future migration into a two-target job rather than an N-target job, and Azure puts the pipeline pain threshold at "often around 10 or more" tenants. It also builds the exact runtime a silo would later need, so tier 3 becomes an increment rather than a restart. For a company with no customers yet, committing to N databases before the first contract is the most expensive promise available.

The one thing tier 2 does not fix on its own is the AI path. A UK database with bid content still being sent to a United States sub-processor will fail a DWP-style offshoring clause, because that clause catches processing and access, not just storage. Scope the AI residency work into tier 2 or the tier does not deliver what it is sold on.

Where a dedicated instance is the wrong answer

When a customer asks for "our own database", they are usually managing one of four risks: another tenant reading their data, us reading their data, data leaving the jurisdiction, or not being able to get their data back. Only the first is addressed by a silo, and it is already addressed for the buyer product by RLS and for both products by server-trusted scoping. The other three are answered by a contract, a region, an encryption control and an export guarantee. Offering a silo in response to a residency question is expensive misdirection: it costs us a fleet and leaves the customer's real objection standing.

#DecisionWhy it is blocking
D1 Do we buy Cyber Essentials now? £320 + VAT, assessor review in 3 working days. It is the only mandated gate for central government and NHS buyers, and it is the cheapest item on this page by two orders of magnitude. There is no argument for deferring it.
D2 Do we commit to tier 2, a London project? Region is chosen at project creation and there is no region-change endpoint. Deciding late means a project migration rather than a project creation.
D3 Do we ship a benchmark opt-out before the next supplier sale? One flag. It converts a disclosure we would rather a customer not discover into a control we can point at.
D4 Do we accept the AI residency position, or scope UK or EEA AI processing? This, not the database, is what a UK offshoring clause will catch. It also determines whether tier 2 can be sold honestly.
D5 Do we give the FastAPI tier an RLS-respecting path? Today the supplier product has single-layer authorisation. The existing test says adding a second model must be deliberate. Deliberate now is cheaper than deliberate after a reviewer finds it.
D6 Do we close the seam gaps found here? The three loadBuyerProfile call sites, and the guard's blind spot for delegated queries. Small work. It keeps the seam honest before anything depends on it.
D7 Do we set a floor price for tier 3? The compute is $15 a month. The operational load is not. A silo sold at compute cost is a loss-making promise that lasts as long as the contract.

What I could not establish

  • How many organisations share the production project. The Supabase MCP returned a permission error on every attempt across the session. One read-only query settles it: select count(*), count(*) filter (where type='council') from public.organisations;
  • Whether the 309-table and approximate-280-table figures reconcile. Both come from production on the same day by different methods.
  • Whether Supabase read replicas require a specific plan. Absent from the docs page, the usage page and the pricing comparison table. The launch blog implies all paid plans with failover on Enterprise.
  • Whether a Supabase region is formally immutable. No page states it. Inferred from the absence of a region-change endpoint.
  • What Supabase BYOC actually is. Confirmed only as a pricing-table row. The documentation page returns 404.
  • A published GBP cost for ISO 27001 certification from any primary source.
  • Whether CrowAgent currently holds Cyber Essentials. Nothing in the repository evidences it, and I did not treat absence of evidence as evidence of absence.
