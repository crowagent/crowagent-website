Solution design

What runs today, and what to build

Three questions, three different answers. The internal portal separates. Buyer and Supplier stay together. Customer tenancy stays pooled, with the seam for a dedicated database built before anyone asks for one.

Every number on this page was counted on production on 29 August 2026. Nothing is estimated. Where a figure is not here, it was not measured, and it is left out rather than guessed.

The internal portal

Separate it. Own repository, own Supabase project. Only 2 foreign keys tie it to customer data, and it holds company financials, salaries, pipeline and board risk.

Buyer and Supplier

Keep them together. The 9 keys that cross are the transaction itself, not debt. Cutting there would cut a contract in half.

Customer tenancy

Pool stays the default. A dedicated database is a premium tier sold when a contract or a regulator demands it. Build the seam now, not the silos.

The dead project

Delete crowagent-internal. No custom domain, Vercel reports "live": false, superseded, and still consuming Actions minutes.

The evidenceThe measurement that decides every cut

One count settles all three questions: how many foreign keys cross each candidate boundary. Counted over every foreign key in public on production.

7portal imports of platform code. All test only, all the same file

The portal is cleanly extractable, and that is not the usual answer. Zero production imports cross in either direction. The whole extraction is publishing five packages by version and copying one test helper.
Why it came out this way, and the file that proves it was on purpose

Shared code was pushed into packages/* rather than reached for across application folders, and the boundary held even where it was inconvenient. web/lib/stripe-prices.ts:52 is the evidence: somebody hit the boundary and, instead of crossing it, wrote down that they could not import from apps/portal.

The 220 shared package imports break down as @crowagent/ui 102, @crowagent/server-infra 93, @crowagent/tokens 15, @crowagent/pricing 7, @crowagent/formatters 3. None of these blocks extraction, because a package can be published and consumed by version.

The seven escaping imports are all web/__tests__/_lib/strip-comments.mjs, and all seven are in test files.

Answer oneWhy the portal separates

Not because a monorepo is bad. Because the company's own confidential data should not share a blast radius with customer data, and nothing is gained by keeping them together.

What separating buysWhat it costs
Portal credentials stop being customer database credentials. Every read becomes an attributable API call under a named identity. One migration to drop 2 foreign keys, plus an API route per read the portal does today.
Different access lists. Anyone who can read the repository today can read the internal tool that manages customers, billing and access locks. A second repository with its own CI and deploy path.
An internal tooling change stops sharing a review and deploy path with the customer product. That is release risk, not tidiness. Publishing 5 shared packages by version, which is worth doing on its own merits.
A monorepo is not a monolith, and the distinction changes the reason but not the answer

A monolith is one deployable that runs as a single unit. A monorepo is one repository that can hold many independently deployable services. Services in a monorepo still build and deploy independently, and CI that detects which service a commit touched rebuilds only that one. So "same repository" is not by itself the bad practice.

The argument for separating the portal is therefore blast radius and access, not code organisation. That matters, because it tells you what else has to change: splitting the repository without splitting the access list and the secrets would be theatre.

The portal holds portal_financials, sales_pipeline, headcount_plan, risk_register, rd_log, mrr_snapshots, portal_documents, portal_approvals, founder_sessions and founder_tasks.

The first version of this page argued the opposite, and it was wrong

It argued that splitting the database would create more of the divergence class that caused a P0 that morning, where one fact lived in four stores that disagreed. That argument is sound for customer data, where 474 foreign keys bind the schema together. It does not apply to the portal at all, and the reasoning generalised from one to the other without counting. The count is what reversed it. The reversal is kept here rather than edited out.

Answer twoWhy Buyer and Supplier do not

The code is already separated. The database is joined exactly where the business is joined, and those nine keys are the product rather than debt.

732supplier files
231buyer files
1,651shared files
3cross imports, all tests, two named after the seam they check
Nine foreign keys cross, and what they are matters far more than how many. A supplier evaluating against a buyer's published requirement. A buyer tracking delivery on a supplier's contract. Social value commitments both sides are held to. A buyer publishes, a supplier responds, a contract is awarded, and both sides are measured against the same commitments. Cutting Buyer from Supplier at the database would cut the contract in half.
The 9 keys, and the full 6 to 3 split
  • crowmark_comparisons.requirement_id to council_requirements
  • contract_kpis.contract_id to crowmark_contracts
  • sv_commitments.contract_id to crowmark_contracts

Buyer to Supplier is 6 keys, Supplier to Buyer is 3.

The three crossing imports are sector-taxonomy-is-not-copied.test.ts, scoring-vocabulary-seam.test.ts and nhs-authority-class.test.ts. They cross on purpose, to assert that a shared vocabulary is not duplicated on both sides.

The open question is a product one, not an architecture one. Whether CrowMark is two tools that share a codebase or one two-sided network is worth deciding, and the architecture already supports both answers. With no real customers yet, nothing is locked in, and the nine keys cost nothing to keep and would be expensive to recreate.

Answer threeWhat we tell a buyer who wants its own database

ModelWhat it meansWhere it belongs
Pool today All tenants in one schema, separated by row level security on a tenant column The default, and what runs now. RLS is on with policies on every table.
Bridge One database, a schema per tenant Rarely the right stopping point. Most of the operational cost of a silo without the audit story.
Silo premium tier A dedicated database per tenant When a contract or a regulator demands it, and the tenant is large enough to pay for it.
Build the seam now, not the silo. Route customer database connections through one resolver that can return a different connection per tenant. That is a small change while there are no silo tenants and an expensive one afterwards. Then a buyer asking for its own database is a configuration and a contract, not a rebuild.
What not to do. Do not split customer data across databases by feature. The 474 foreign keys say the customer schema is one system, and cutting it by feature is what puts the same fact in several places. Splitting by tenant is a different operation and does not have that problem, because one tenant's rows do not reference another tenant's rows.

Tenancy is covered in full, with the code evidence and the region question, under Tenancy and isolation in the switcher at the top of this page.

The workThe sequence, in order, no conflicts

0
Delete the dead portal. Remove the crowagent-internal Vercel project, archive the repository. No custom domain, "live": false, superseded. Stops its Dependabot runs consuming Actions minutes. Irreversible, so it needs the owner. Nothing else depends on this step.
1
Cut the two foreign keys. platform_connector_apps.organisation_id and platform_connector_connections.organisation_id become plain identifiers. One migration. After this the portal schema references nothing customer side and the split is a copy rather than surgery, so every later step is cheaper.
2
Create the portal Supabase project and move the 26 tables. The portal_, founder_ and platform_ tables plus health_history, sales_pipeline, headcount_plan, rd_log, risk_register, mrr_snapshots and infra_cost_history, with their 13 internal keys intact. Staging first, verified row for row, then production.
3
Give the portal a service identity on the platform API. Named credential, explicit scopes, audit trail. Replace the portal's remaining direct reads of customer tables with API calls. This is the step that turns a shared secret into a revocable one, and it is the real security win.
4
Publish the shared packages by version. tokens, ui, formatters, pricing. Worth doing even if nothing else happens, because today a token change forces the customer product to rebuild.
5
Extract apps/portal into its own repository, with separate access and secrets. History preserved, its own CI, its own deploy. Do the access list and the secrets at the same time or the split is cosmetic. Last, because steps 1 to 3 deliver most of the security benefit without it.
6
Build the tenant connection seam. Do not build silo tenants. One resolver that can return a different connection per tenant. Cheap now, expensive later.
Every structural change here is at its cheapest right now. No customer data to migrate, no uptime to protect, no contract to renegotiate. The portal split, the tenant seam and the shared package publishing are one-time costs that rise the moment a real customer arrives.
