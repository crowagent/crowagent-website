Release and environments

Local to staging to production, one direction, one path

Code reaches production only by promotion. It is built and proven on staging at the same commit, recorded in a ledger, and pushed by one script that refuses to run without a verified record, a green billing audit and the owner's approval text. No push by hand, no dashboard deploy, no merge button.

Measured 4 September 2026 from the Vercel REST API, the Railway API and CLI, both Supabase projects, the Stripe API and the GitHub CLI. First production promotion through this path: commit ca75732d, 4 September 00:33 UTC.

Why staging costs nothing and cannot start billing by accident. The staging front end is a Vercel custom environment with no branch tracking, so no git push can ever build it. Both Vercel projects sit on a fixed Standard build machine with Elastic and on-demand concurrency off, and Vercel bills Standard builds only when one of those is on. The audit fails the moment either is switched on.

Section 2How to promote to staging

Run from crowagent-platform/ on main. Only committed code travels: the script exports HEAD with git archive into a scratch directory, so a dirty working tree is refused.

1
Commit the work. Every change on local main, by pathspec, never git add .. The tree must be clean apart from untracked files.
2
pnpm staging:promote Runs scripts/staging/promote-staging.mjs: export HEAD, vercel pull --environment=staging, vercel deploy --archive=tgz --target=staging. Vercel builds it on the fixed Standard machine with the production install command, which is the deploy rehearsal RULE 0-D asks for. No GitHub Actions minute, no push, no git deployment. Takes about five minutes.
3
The script proves the surface before it records anything. Deployment READY in the staging custom environment with no git metadata, then https://staging.app.crowagent.ai/login answers 200 with x-ca-env: staging and x-robots-tag: noindex. Only then is a line appended to scripts/staging/promotions.jsonl with verified: false.
4
Prove the change on staging, targeted. The e2e gates that cover the change, run against the staging URL, for example BASE_URL=https://staging.app.crowagent.ai npx playwright test e2e/<file> --project=chromium --no-deps. RULE 0-T: the files that cover it, one invocation, never the whole suite. Beta testers do their pass here.
5
pnpm staging:verify --sha <full sha> --by "<who>" --note "<what was proven>" Marks the ledger record verified. The note names the evidence. Without this the production script will not run.
Two traps measured on the first day. A prebuilt upload built on this Windows machine (--prebuilt) answered MIDDLEWARE_INVOCATION_FAILED on every route with no log, so the default is a source upload and Linux builds it. And Vercel Authentication treats a custom environment domain as a preview, so it was gating staging behind a Vercel login. It is now off on the web project, and the $150 a month password add on is never enabled.

Section 3How to promote to production

1
The owner approves, in words that name the commit. One approval is one push. The approval text must contain the first seven characters of the sha being promoted. A standing "yes" from an earlier message is not an approval.
2
pnpm prod:promote --approval "<owner text containing the sha7>" Runs scripts/staging/promote-production.mjs. It aborts on the first failed precondition, in this order: clean tree, on main, a verified staging record for the product tip (for a merge commit that is the second parent, and commits that touch only the ledger, the hook, docs or root markdown are walked back over, because they cannot change the artefact), the live billing leak audit, then the approval text.
3
It prints the cost before it spends anything. Which workflows fire on a push to main (four today), whether the portal builds (only for a merge tip or a change under apps/portal or packages), and that Railway redeploys three services. Then it runs the one git push origin main with CA_PUSH_APPROVAL set.
4
The pre-push hook is the backstop. .husky/pre-push refuses any push to main without the matching CA_PUSH_APPROVAL and a verified record, refuses any branch named staging, and runs the quick audit. A raw git push is blocked, as it was on 3 September when it caught six workflow files still carrying schedule triggers.
5
Audit after the push, every time. Web READY on the sha, portal READY or correctly CANCELED, Railway 3 of 3 SUCCESS, the workflows green, then the product proof on app.crowagent.ai: x-ca-env: production, no beta banner, and the gate that covered the change run against production. Record it on the tracker row.

Vercel deploys a change of environment variable only on the next deployment. A variable set in the dashboard is therefore paired with a promotion, never assumed live.

Section 5The guardrails and what each one measures

pnpm billing:audit runs scripts/staging/billing-leak-audit.mjs, thirteen checks, each red proved in its test file. --quick runs the five repo checks without the network and is what the pre-push hook uses. Any FAIL row is a P0.

The audit is never wired into CI (RULE 0-G): it is run before every promotion, after any infrastructure change, and weekly by hand. A timer would be the thing it exists to catch.
