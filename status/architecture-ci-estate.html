Cost and control

Every job we run, and what it costs

GitHub costs about ten times Railway. The bill is not the crons and never was, it is the two workflows that gate a merge, billed per job with round up. The cap is now $15 a month with stop usage on, which is the backstop rather than the fix.

Measured 29 August 2026 from the live GitHub API, the GitHub organisation billing console, the Railway console, the production Supabase cron.job table and the Railway scheduler source.

I recommended before measuring, and measuring reversed it.

Lighthouse CI has failed 19 of its last 19 runs and gates nothing. It is not a required check, so a red run blocks no merge, and it has never been green, so nobody reads it. That is a workflow which bills on every pull request and reports to no one. It is either fixed and made to mean something, or deleted. Leaving a permanently red job wired to nothing is the exact pattern RULE 0-G exists to stop: a gate that is always red teaches everyone to ignore gates.
What NOT to cut, and why blind cutting would be wrong
  • The two gating workflows stay. They are 76 percent of the bill and the only thing between a broken commit and main. Removing them removes the safety net, not the cost.
  • Dependabot stays. 47 minutes in the measured window is dependency vulnerability work, not overhead, and there is no equivalent off GitHub.
  • Dispatch-only workflows stay. Eight of the thirty bill nothing while idle, so deleting them saves no money and only loses a tool. Same rule as RULE 0-G's point about a gate not wired into CI: if it does not run, it does not bill, and it is not the problem.
  • Concurrency cancellation is already correct on both gating workflows, and correctly refuses to cancel an in-flight run on main or staging. The usual free win here is already taken.

Section 4The rule, and the cheapest real saving

The rule: GitHub keeps only what nothing else can do. Railway takes everything that does not need to answer a pull request. GitHub Actions is the only thing that can report a status check back to a pull request, which is what branch protection enforces. That is a genuine monopoly and worth paying for. Everything else runs on a timer or produces a report nobody merges against, and Railway already runs that class free at the margin.
LayerKeepsWhy it is the right home
GitHub ActionsThe 2 required checks, plus DependabotOnly surface that can gate a merge. Dependabot has no equivalent elsewhere.
RailwayScheduled audits. Price drift, smoke test and robots guard are already thereThe container is always on and billed anyway, so each added job costs only its CPU seconds. Proven with ~29 live jobs.
Supabase pg_cronProduct cron that drives app endpointsAlready correct. Scheduling happens inside Postgres at no extra cost and stays next to the data.
This machineEvery build, typecheck and test before a pushRULE 0-G already mandates local first. CI is the gate, never the test runner.
1
Reduce the JOB count in the two gating workflows. 21 jobs, each rounded up to a whole billed minute, on every push. This attacks the 76 percent directly and changes no behaviour. It matters MORE now that the true driver is known to be per job round up rather than wall clock time.
2
Resolve Lighthouse CI. 19 of 19 red while gating nothing. Fix it and make it a required check, or delete it. Do not leave it billing on every pull request and reporting to nobody.
3
Move the remaining scheduled audits to Railway. Three are already there. The rest removes all unattended overnight spend at zero marginal cost, though at 2 percent of consumption the saving is small and it is worth doing for the discipline rather than the money.
4
Fold the small non-gating pull request checks into the gate. One runner does the work of six, and the six stop each paying a start up minute.

100 percent of the metered GitHub spend is Actions, and an earlier version of this page said it probably was not. The timing API returned zero billable milliseconds and the PERSONAL account showed no usage. Both were true and both were the wrong place to look: the repositories belong to the crowagent ORGANISATION, which bills separately.
The 17 August cron cut worked, and the chart proves it. Cumulative spend climbed at $3.33 a day up to 17 August and $0.70 a day after it, a 79 percent reduction in run rate. Most of the $40 is damage already done earlier in the month rather than an ongoing rate.

Three products already carried hard $0 ceilings with stop usage enabled. Actions carried $100 a month, roughly five times what the work needs, so it permitted the overspend instead of stopping it. Owner decision 29 August 2026: $15 a month, an 85 percent cut, stop usage ON. Still about four times the post-17-August run rate, so ordinary work never reaches it. Because $40.23 was already spent this month the budget reads Over budget immediately and Actions is halted for the remaining two days of August, resetting on 1 September. With no approved push outstanding that costs nothing.

Where this leaves the recommendation.
  1. The $15 cap is the permanent backstop, not the fix. Worst case is $15 a month instead of $100, and a runaway workflow halts rather than bills.
  2. Consolidating the 21 jobs is the first real fix. It costs nothing to run and keeps every gate.
  3. A self hosted runner is now genuinely worth considering, which my earlier estimate got wrong. About $9.65 of Railway usage against $39.80 of GitHub Actions saves roughly $27 a month once the work exceeds the cap. Consolidating first shrinks what has to be relocated.
