Release and environments

Local to staging to production, one direction, one path

Code reaches production only by promotion. It is built and proven on staging at the same commit, recorded in a ledger, and pushed by one script that refuses to run without a verified record, a green billing audit and the owner's approval text. No push by hand, no dashboard deploy, no merge button.

Measured 4 September 2026 from the Vercel REST API, the Railway API and CLI, both Supabase projects, the Stripe API and the GitHub CLI. First production promotion through this path: commit ca75732d, 4 September 00:33 UTC. Corrected on 4 October 2026 against promote-staging.mjs, promote-production.mjs, scripts/vercel-build-ignore.sh, the live Railway API and a curl of every host. Refreshed on 9 October 2026 after the production promotion of 9031f5fd1 (8 October), the full key rotation and the two incidents it caused: Stripe, Supabase keys, the portal ignore command, the variable stores and the key runbooks (D and E) were re-measured. Section 2How to promote to staging

Run from crowagent-platform/ on main. Only committed code travels: the script exports HEAD with git archive into a scratch directory, so a dirty working tree is refused.

1
Commit the work. Every change on local main, by pathspec, never git add .. The tree must be clean apart from untracked files.
2
pnpm staging:promote Runs scripts/staging/promote-staging.mjs: the 33 local quality gates in a clean checkout of HEAD (waive one run with CA_SKIP_QUALITY_GATES=1, which the record announces), export HEAD, vercel pull --environment=staging, vercel deploy --archive=tgz --target=staging. Vercel builds it on the fixed Standard machine with the production install command, which is the deploy rehearsal RULE 0-D asks for. No GitHub Actions minute, no push, no git deployment. Web is the default. The portal is its own run, pnpm staging:promote --project portal, after the web record is committed, because the web run leaves promotions.jsonl dirty. The run downloads .env.staging.local, which holds staging keys, into ~/crowagent-scratch/promote/<sha>/.vercel/. Delete those folders once the record is committed.
3
The script proves the surface before it records anything. Deployment READY in the staging custom environment with no git metadata, then https://staging-app.crowagent.ai/login is smoke tested. Since 13 September every staging host sits behind Cloudflare Access, so a plain request answers a 302 to the Access login. The script records that honestly as smokeReachedApp: false rather than failing or pretending. Prove x-ca-env: staging and x-robots-tag: noindex yourself with the Cloudflare service token before you verify the record. A line is appended to scripts/staging/promotions.jsonl with verified: false.
4
Prove the change on staging, targeted. The e2e gates that cover the change, run against the staging URL, for example BASE_URL=https://staging-app.crowagent.ai npx playwright test e2e/<file> --project=chromium --no-deps. RULE 0-T: the files that cover it, one invocation, never the whole suite. Beta testers do their pass here.
5
pnpm staging:verify --sha <full sha> --by "<who>" --note "<what was proven>" Marks the ledger record verified. The note names the evidence. Without this the production script will not run.
Two traps measured on the first day. A prebuilt upload built on this Windows machine (--prebuilt) answered MIDDLEWARE_INVOCATION_FAILED on every route with no log, so the default is a source upload and Linux builds it. The same failure took production web down on 29 September when the production script still built locally, so production now uses the source upload too. And Vercel Authentication treats a custom environment domain as a preview, so it gates staging behind a Vercel login whenever it is on. It has been switched off and on more than once since, so its current state is unverified: curl the host with the service token and read which gate answers, never the Vercel API. The $150 a month password add on is never enabled.

Section 3How to promote to production

1
The owner approves, in words that name the commit. One approval is one push. The approval text must contain the first seven characters of the sha being promoted. A standing "yes" from an earlier message is not an approval.
2
pnpm prod:promote --approval "<owner text containing the sha7>" Runs scripts/staging/promote-production.mjs. It aborts on the first failed precondition: clean tree, on main, a verified staging record for the product tip (for a merge commit that is the second parent, and commits that touch only the ledger, the hook, docs or root markdown are walked back over, because they cannot change the artefact), the live billing leak audit, the local quality gates at the sha, then the approval text.
3
It prints the cost, then deploys, because git no longer does. Since 26 September (owner option A) a push to main builds nothing on the web project. The cost statement lists the workflows that fire on a push to main (four files carry that trigger, three of them path filtered). The portal's ignore command now skips git builds too (0745f7464): the 8 October push of 9031f5fd1 produced 4 git deployments across web and portal and all 4 settled CANCELED. Then, in order: git push origin main with CA_PUSH_APPROVAL, which is the record of what production runs. Only when api/ changed, the same sha to railway-production, which deploys crowagent-platform and crowagent-worker. Then web and portal as source uploads, vercel deploy --prod --archive=tgz, built on Vercel. The script's header comment still says prebuilt. The code is the truth.
4
The pre-push hook is the backstop. .husky/pre-push guard 0a refuses any branch named staging, 0b refuses main without the matching CA_PUSH_APPROVAL and a verified record, 0c runs the quick audit, 0d runs the local quality gates on a raw push to main, and 0e refuses railway-production without approval. A raw git push is blocked, as it was on 3 September when it caught six workflow files still carrying schedule triggers.
5
Audit after the push, every time. The script verifies every target against the pushed sha and exits 1 on a partial deploy, which is never reported as done. Then the product proof on app.crowagent.ai: x-ca-env: production, no beta banner, and the gate that covered the change run against production. Record it on the tracker row.

Vercel deploys a change of environment variable only on the next deployment. A variable set in the dashboard is therefore paired with a promotion, never assumed live.

Section 6Cutover runbooks and the rules of the road

A
Stripe live cutover, done 4 September. Live webhook endpoint created for app.crowagent.ai/api/stripe/webhooks, the archived live CrowMark product reactivated (its lookup keyed prices would have failed checkout), live secret key pasted by the owner into Vercel and Railway, live webhook secret and mode written by the cutover script, one promotion. Staging stays on the sandbox for ever. Measured 8 and 9 October: the production key is live but the mode flag reads test, see section 1. That disagreement is the owner's to settle.
B
Production data is the four accounts in one organisation. Five test accounts and their organisations were deleted on 3 September, then the three personal organisations were merged into CrowAgent. A snapshot of every deleted row sits in crowagent-scratch/. Any future test account on production is a defect row.
C
The documents that bind. crowagent-platform/docs/ENVIRONMENT-PROMOTION-MANDATE.md (one page, binding on humans and AI), docs/PRODUCTION-CUTOVER-RUNBOOK.md, RULE 0-P in ENGINEERING-STANDARDS.md and the root CLAUDE.md. When a convenience and the document disagree, the document wins. If a step is impossible, stop and put the question to the owner with the cost in numbers.
D
Rotating a key, in this order (learned 8 October 2026). Create the new key. Put it in every store that holds it: Railway services, Vercel production AND the Vercel staging environment, the portal Integrations table, the local .env.local files. Fingerprint each store to prove they match, never print a value. Rebuild what reads it, because Vercel applies a variable only on the next build. Prove it on /readyz and a live page. Only then revoke the old key. Getting this wrong cost two incidents on 8 October: about an hour of production API errors when the old Supabase secret was revoked first, and every signed in page down when a staging key reached a Vercel production variable. The rules for every AI tool are in the onboarding guide, section 3.7.
E
Restoring production after a bad variable. An instant rollback to the last good deployment (vercel rollback <url>) needs no build and restored web and portal within seconds on 8 October. After a rollback the next build does not take the domain by itself, so promote it explicitly (vercel promote <url>). Then correct the variable and rebuild. Only the driver does this, and the owner is told straight after.

Section 7Testing on staging: credentials and headless access

Added 2 October 2026 (R2.8.4). The staging URL is https://staging-app.crowagent.ai with a hyphen, not a dot. An earlier version of this page wrote staging.app.crowagent.ai, which does not reach the app (it answered 403 on 4 October). The canonical promotion mandate always had the hyphen, and this page has been corrected to match it.

Staging has up to THREE gates in series, and a headless test must satisfy each one that is on. Cloudflare Access first, then Vercel Authentication when it is switched on, then the app's own Supabase login. A browser session a human opens passes them interactively. An automated run passes them with request headers plus a programmatic sign in, no headed PIN and no dev server.

The two harnesses that already wire this. The Playwright discovery config web/playwright.discovery.config.ts injects the Cloudflare service token and the Vercel bypass as extraHTTPHeaders, and its specs sign in with signInWithPassword and write the session cookies (web/e2e/_supabase-session-cookie.ts). Run a discovery spec from web/ with BASE_URL=https://staging-app.crowagent.ai npx playwright test --config=playwright.discovery.config.ts e2e/r284-discovery/<spec>. The AI cost-measurement runner api/tests/ai_golden/live_eval_r283_http.py signs in the same way, and from R2.8.4 it also sends the Cloudflare service-token headers on every app-host call, because without them the app's first edge gate 302s the request before it reaches the BFF.

Two credential traps. The Supabase "publishable key" the runner asks for (STAGING_SUPABASE_PUBLISHABLE_KEY) is the staging NEXT_PUBLIC_SUPABASE_ANON_KEY, nothing separate. And a guard that checks the staging project ref must read it from NEXT_PUBLIC_SUPABASE_URL (which contains ipgrnwvfnumgvnxkpxsc as plain text), never from the anon key. Since 8 October the anon key is an sb_publishable key, which carries no project ref at all, and the old JWT anon key is disabled.
