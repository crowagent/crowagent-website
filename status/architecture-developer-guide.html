Developer guide

From a clean checkout to a production promotion

Three deployables, one monorepo plus the marketing site. The web app and the portal are Next.js on Vercel, the API is FastAPI on Railway, the site is Astro on Cloudflare Pages. Everything is verified on this machine first, promoted to staging, then to production by one script. CI is a backstop that fires on the push, never a test runner.

Commands read from package.json (root, web, portal, astro), the API Procfile, .github/workflows and web/playwright.config.ts on 4 September 2026. Corrected on 4 October 2026 against the scripts, the workflow files and the live Railway API. The single onboarding source for every AI tool is crowagent-platform/docs/AI-ONBOARDING-GUIDE.md, and where this page and that guide disagree, the guide is the newer measurement.

Section 2Set up and run locally

1
Install, three package managers on purpose. Root and portal FIRST: pnpm install --frozen-lockfile. Then web: cd web && npm ci, so npm is the last writer for web/ (Vercel installs the web project with npm against web/package-lock.json, and packages/ui is installed standalone with npm, so its dependencies are exact pins). API: the pinned set lives in api/.venv, install into it with ./.venv/Scripts/python.exe -m pip install -r requirements.txt. Never use the global python, it carries a different FastAPI. Node 24 everywhere, pinned in the root engines.
2
Environment files. web/.env.local targets staging Supabase and staging Railway and is gitignored. Copy web/.env.example for a fresh machine. Never copy from web/.env.local.staging-bak, it names a Supabase project deleted in July. The pre-commit hook refuses any .env file and any commit that carries the owner's personal identity.
3
Start servers detached, never inside a tool call. Web: cd web && npm run dev (3000). Production bundle for gates: cd web && CA_BUILD_LOW_CPUS=4 npm run build && npm run start (3001). Portal: cd apps/portal && pnpm dev -- -p 3100. API: cd api && uvicorn app.main:app --reload --port 8000. Board: crowagent-website/status/start-tracker.cmd. On this machine a server started inside a tool call dies with the tool's timeout, so use Start-Process in PowerShell and stop by verified pid, never by process name.
4
Build facts that cost hours to learn. CA_BUILD_LOW_CPUS=4 makes next build finish here, =1 never does. A build in web/ while next start holds 3001 hangs both: stop 3001 first. web/.next/dev/cache grows past 4 GB and survives restarts. Delete it by path when a chunk looks stale. A green local build proves the source compiles against the node_modules you happen to have, not that the deploy installs the same tree (RULE 0-D). Staging is the rehearsal.

Section 3Verify a change: type check, tests, gates

RULE 0-T. Run the files that cover the change plus their guard, batched into ONE invocation for API pytest. On web/ vitest a multi file run fails to start workers here, so run those one file at a time and read each collected count. A full suite is a certification act at the end of a release, never a way to check a fix. Check free RAM first and never start a heavyweight below 2 GB free (RULE 0-L).

Section 5Database and migrations

1
Apply through the Supabase MCP, never the CLI and never db push. Either re-runs about a thousand already applied migrations (1,004 files on 4 October), several with DROP TABLE. Write migrations in ASCII only, and ship any migration that changes what deployed code reads or writes in the same promotion as that code. Prefer execute_sql for DDL. After ANY apply, write the migration file into supabase/migrations/ with a unique, correctly sorting version: the file is the record, not the stamp.
2
Staging first, then production, both by the same file. The schema guard checks code against STAGING, never staging against production, so a green guard says nothing about production. Twenty five production tables have no creating migration for exactly this reason.
3
Know the traps. A referential action is a real UPDATE or DELETE and fires the immutability triggers on the ledgers: deleting an organisation with an audit row aborts unless the eleven triggers are disabled and re-enabled inside the same transaction. org_trust_pages and org_trust_share_tokens are NO ACTION foreign keys and must be pruned by hand. RLS denial is a 200 with an empty array. Policy helpers live in private, not public.

Section 6The end to end pipeline

1
Work on local main, commit by pathspec. Every commit names its tracker row (R282-...) and states what was measured. git add . is forbidden in the shared tree. Nothing is pushed.
2
Verify locally, targeted. Types on both tsconfigs, the unit files that cover the change in one invocation, the e2e gate that covers it against 3001, the arch and brand lints if code moved.
3
pnpm staging:promote Clean tree required. The 33 local quality gates run first at the sha, then the upload, which Vercel builds on the unbilled Standard machine. Smoke proves the staging surface, the ledger gets a record. The portal is a second run with --project portal, after the web record is committed.
4
Prove it on staging, then pnpm staging:verify --sha <full sha> --by "..." --note "..." The gates that cover the change, run against the staging URL. Beta testers use the five beta tenants. The note names the evidence.
5
pnpm prod:promote --approval "<owner words with the sha7>" Clean tree, main, verified record for the product tip (ledger and docs commits are walked over), live billing audit, approval text, cost statement, one push. The pre-push hook enforces the same rules on a raw push, so there is no second path.
6
Post push audit and product proof. The script itself verifies web and portal READY from the deployments it uploaded, and Railway crowagent-platform and crowagent-worker on the sha when api/ changed. A partial deploy exits 1 and is never reported as done. Then the change is proven on app.crowagent.ai and written on the tracker row. Website: a push to main is a Cloudflare deploy and needs its own approval.

Budget: zero pushes per session by default, a hard ceiling of two even with approval, no reruns, no workflow_dispatch, no non draft PR without a separate ask. State the cost before asking: which workflows fire and whether a deploy triggers. CI is never a test runner: a red run is reproduced and fixed here first, and a remote run is a last resort for something that genuinely cannot run locally.
